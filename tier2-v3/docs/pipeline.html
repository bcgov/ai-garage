Tier 2 v3 pipeline

A spec-driven delivery loop for BC Gov services. Work moves through versioned artifacts in git — intent, spec, plan, code — with three points where a named human must agree before work continues. Coding agents can draft at every stage; they never merge on their own.

Front door: every change, including production fixes, re-enters through the same path. GitHub pull requests and CI checks are the audit record. There is no separate “fast lane” that skips the paper trail.

Enrol the repository (one time)

Install the Tier 2 v3 pattern pack into a service repo so the scaffolding, workflows, and gates exist before the first slice of work.

  • Run enrol.sh to copy GitHub Actions workflows, a constitution template, Spec Kit files, review policy (REVIEW.md), and pack config (tier2-v3.config.json).
  • Optionally enrol Tier 1 alongside for issue triage, docs-drift checks, and automatic intent-ready labelling on well-formed issues.
  • Replace placeholder teams in CODEOWNERS so humans — not agents — control changes to gates and acceptance criteria.

Exit: preflight workflow passes; repo is ready for a pilot slice.

Preflight workflow
1

Capture intent (who is stuck, and why)

Work starts as a problem statement, not as code. Program staff describe who is affected and what outcome they need — without needing git fluency.

  • Someone files a GitHub issue with Problem, Outcome, and optional Evidence (research, incidents, support data).
  • When the issue is ready, add the intent-ready label (or let Tier 1 triage add it automatically).
  • The promote-intent workflow opens a draft PR with intent/{slug}.md — a durable record of motivation before anyone writes a spec.

Exit: product owner accepts the intent PR. The issue was a proposal; the intent file is the first agreed artifact.

Promote-intent workflow Review intent PR
2

Write the spec and acceptance criteria

Turn intent into a testable contract: what the system must do, written in plain language and Gherkin scenarios. This is what implementation will be checked against.

  • spec/spec.md describes the behaviour in technology-neutral terms (problem, outcome, scope).
  • spec/features/*.feature holds Given/When/Then scenarios. Each scenario gets a permanent ID tag, e.g. @R-14.1, so tests and reviews can point to a specific promise.
  • constitution.md (articles P1–P8) sets non-negotiables: accessibility, design system, privacy, deployment platform, and similar ministry standards.
  • An agent may draft spec text; a human product or tech lead must agree before coding starts.

Exit: checkpoint 1 — “we agree what to build.” Chat and issue text are no longer authoritative once spec is signed.

Checkpoint 1Agent may draft
3

Plan the approach

Before code changes land, the team records how they will build the slice — architecture, risks, and task breakdown — so agents and humans share the same plan.

  • spec/plan.md explains the technical approach, trade-offs, and what is explicitly out of scope.
  • spec/tasks.md breaks work into implementable rows an agent or developer can pick up one at a time.
  • For high-risk criteria, tag the scenario with @tier:high to force full pipeline ceremony (plan and features required, not relaxed).

Exit: checkpoint 2 — “we agree how to build it safely and at a sensible size.”

Checkpoint 2
4

Implement (agents draft, humans own merge)

Code is written against the signed spec and plan. Agents speed up drafting; they open pull requests but do not merge them.

  • Local path: developer uses an IDE agent with MCP (design system, SDLC policy) and opens a draft PR from their machine.
  • Cloud path: add ready-for-agent on the issue; Copilot coding agent opens a draft PR (requires COPILOT_ASSIGN_TOKEN).
  • Acceptance tests should declare which criterion they prove, e.g. // criterion: @R-14.1 at the top of the file — so reviewers can trace test → promise.
  • Update docs/pr-evidence.md when the pack requires it, summarizing what was verified for this PR.

Exit: draft implementation PR opened; CI will run on push.

5

Automated gates on the pull request

CI checks that the paper trail matches the code before a human spends review time. Agents may comment; deterministic checks block when required artifacts are missing.

  • Risk triage labels the PR tier2-v3:direct or tier2-v3:pipeline. Small, low-blast-radius changes may warn instead of fail on missing plan/features; everything else needs full ceremony.
  • Checkpoint gate verifies constitution, spec, plan, and feature files exist for the paths touched. Warns if Gherkin scenarios lack @R-xx.y IDs.
  • Provenance check warns when acceptance tests do not name the criterion they derive from.
  • Spec review posts a heuristic or LLM comment tracing the PR to spec; redaction guard blocks secrets in public comments. Warns if the PR body lacks a review receipt.

Exit: gates green or warnings understood; PR is ready for human ship decision. Do not disable workflows to “make CI green” — fix artifacts or scope instead.

Checkpoint gate Provenance Spec review
6

Ship (human merge)

A named reviewer decides whether the change matches what was agreed — and records what they could not verify. Only then does code reach the default branch.

  • Compare the PR to spec/features, plan, and constitution articles cited in the PR.
  • Post a review receipt in the PR: what you checked, what you could not check, and any residual risk you accept.
  • Merge manually. Branch protection should prevent bots from self-merging.

Exit: checkpoint 3 — “this matches what we said we would ship.” Code is on main; criterion coverage metrics can advance to implemented/verified.

Checkpoint 3 · merge
7

Measure and close the loop

Delivery does not end at merge. The pack watches lead time, gate friction, and criterion coverage — and feeds production signals back through the same front door.

  • Weekly metrics artifact: intent→spec→plan lead time, rework cycles, per-criterion coverage states, and cost-of-judgment proxies (review turns, days at checkpoint).
  • Maintain loop watches metric bands; at 3σ it drafts intent/maintain-{date}.md and opens a draft PR — never auto-merges. On-call triages: fix, schedule, or tune bands.
  • Production issues and drift re-enter as intent → spec → plan, same as greenfield work.

Exit: team learns from exhaust; the loop repeats for the next slice or maintain fix.

Direct vs pipeline mode

Not every code change needs the full spec → plan → features apparatus. Triage picks the ceremony level per PR:

  • Direct — typically ≤3 files, only under allowed paths (e.g. src/), low reference count, additive edits. Missing plan or features may warn instead of fail.
  • Pipeline — default when uncertain, when git checks are inconclusive, or when any scenario carries a real @tier:high tag. Full ceremony required.

When in doubt, the pack chooses pipeline. A small change sent through extra review costs time; a large change in direct mode costs correctness.

What lives in git (the system of record)

  • constitution.md — ministry non-negotiables (P1–P8)
  • intent/*.md — motivation and evidence before spec
  • spec/spec.md, spec/features/*.feature, spec/plan.md, spec/tasks.md — the contract chain
  • docs/pr-evidence.md — what was verified for a given PR
  • REVIEW.md — shared review policy and receipt format
  • tier2-v3.config.json — gate thresholds, review mode, triage rules
